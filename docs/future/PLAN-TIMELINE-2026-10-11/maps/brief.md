# Brief: what the nine readers found at HEAD e2cdc4e

Each area below has a full map with every fact and file:line citation at maps/<area>.md in this directory.

## contract

### Summary
A note's format is decided per provider today, never per note. Each provider declares `readonly property bool markdown`, plus `hasTitle`, `canImages` and optionally `tools`, on its live QML instance; the plugin manifest declares no capabilities. The host reads these off whichever provider owns the open note's path. Workspace.qml:2831-2848 binds the editor's canImages, plain (= !p.markdown), hasTitle and enabledTools to providerOf(currentPath). `plain` is the only thing the markdown flag switches, and it switches a lot: Markdown<->HTML conversion in setNote, requestMarkdown and snapshotDocument; TextEdit's textFormat; paste; every block-editing helper and the decorations; and, through EditorApi.writable, the whole toolbar and every tool. Nothing else reads markdown: sidebar.js, previews (computed by providers), search and NoteSession never look at it. hasTitle reaches the editor's title field, the focus choice after create, and (via sidebar.js row()) the bold first line in the list and in search results. tools and canImages gate the toolbar, the tool shortcuts and the rich and image paste. Creation has exactly one call site, p.create(target, cb) in Workspace.newNote (1912). Footer actions (provider action -> host.newNote), Ctrl+N and the palette (WorkspaceActions -> the first footer marked shortcut newNote, else createTargetFor), rows of kind new, and createSection's target all funnel into it. target is an opaque string the provider owns ("section:<key>", "parent:<id>", "new"), and no options channel exists anywhere on the create path. On cb({path}) the host reports errors, switches to the note's tab, calls choosePath (which remembers the note, then session.selectPath -> load), scrolls to the row, and focuses the title only if p.hasTitle; provisional notes later emit notePathChanged, which NoteSession.replacePath applies without a reload. The load answer is consumed only in NoteSession.load (246-300), which reads error, version, base, title, body, view, editable, reason, recovered, conflict and retry before calling editor.setNote. Drafts bypass load through restoreDocument, and OneNote's script already emits a per-page `markdown: true` that nothing reads. Rows pass through a whitelist in sidebar.js:24-31, so an extra field such as `type` is silently dropped: harmless to add on the provider side, but the list can only use it once row() copies it and NoteList/NoteSummary show it, which decisions.md:444-448 requires. Note rows have no icon slot. The defaults for absent members are inconsistent. Absent markdown means plain text. Absent hasTitle counts as true in sidebar.js and as false in newNote, and the editor binding keeps its previous value with a QML warning (verified on Qt 6.11.2). Absent canImages means false, and absent tools means all. The compatibility precedent to follow is canReorder/setOrder -> per-row reorder plus async reorder(): the legacy shorthand stays, an explicit per-item value wins (null included), and the host feature-detects modern versus legacy. The other precedents are optional trailing options (save), ignorable extra arguments (action), optional hooks with host defaults (noteEdited) and the 1.x legacy-directory adapter. The contract must change additively, apiVersion must stay 1, and docs/providers.md and the skill reference must change in the same commit; the two have already drifted.

### Recommendations
- Follow the canReorder -> reorder precedent: keep `markdown` as a documented legacy shorthand for a provider's default type, add an explicit per-note type that wins when present, feature-detect it in one host helper, and document the mapping in a compatibility paragraph modelled on docs/providers.md:170-175.
- Pass the requested type to create through an optional trailing options object so two-argument create(target, cb) providers keep working (precedent: save options, docs/providers.md:283-291). Never encode it in the opaque target.
- Normalise all capability defaults (markdown, hasTitle, canImages, tools and the new type data) in one place, and fix the Workspace.qml:2841-2844 binding so an absent hasTitle no longer inherits the previous note's value.
- Amend docs/providers.md, skills/note-note-plugin/references/providers.md and examples/hello in one commit, reconciling the existing drift. Keep apiVersion 1, and keep the legacy hello test (tests/standalone_launch.qml:38-40) passing unchanged.

### Risks
- A per-note type carried only on rows cannot drive the editor: created notes may not be listed yet, and drafts restore without load (NoteSession.qml:235-245). The editor mode needs the type from the load answer and from the draft snapshot ({title, body, base} today, NoteEditor.qml:318-321).
- The editor mode bindings (Workspace.qml:2831-2848) switch when currentPath changes, before load answers, and setNote reads `plain` synchronously (NoteEditor.qml:300). A per-note type must be applied before setNote runs, or a note renders and saves in the wrong mode.
- Defaults for absent capabilities are already inconsistent. Absent hasTitle is true in sidebar.js:26 and falsy in Workspace.qml:1932, and the editor binding at Workspace.qml:2843 keeps its previous value with a warning (verified on Qt 6.11.2). New per-type reads without one normalising function would multiply this.
- An absent `markdown` silently means plain text (Workspace.qml:2839) and docs/providers.md:47 does not say so. Any mapping from markdown to a default content type must keep that meaning for existing external providers.
- Encoding the requested type in the opaque create `target` would be a hack (CLAUDE.md:3): providers parse their own target strings (local Provider.qml:556; OneNote 1135-1141; Notion 248).
- A host-generated 'New timeline' button or menu item contradicts docs/providers.md:100-101 and 185 unless those rules are amended. Ctrl+N fires only the first footer action marked newNote (Workspace.qml:1690-1703).
- A provider calling host.newNote from inside rowAction before answering is ignored: the session is locked (Workspace.qml:2115-2116) and newNote returns while locked (1888-1890).
- Kind 'new' rows always render '+ New note…' (ui/NoteList.qml:472-473, 485), so a typed creation row needs UI support as well as contract text.
- Local read marks a note read-only when unkept(body) reports constructs the rich-text writer cannot keep (operations.py:19-31, 111-121). A timeline body format must pass that check, or the check must be skipped for non-Markdown types.
- Previews and content search work on the raw body (notefile.py:79-86; sticky Provider.qml:52-61, 163-171; local search via Provider.qml:359-366), so a serialized timeline shows its raw syntax in the list and matches on its markup.
- Backend writers refuse constructs they cannot keep (OneNote refuse_unkept_formatting at onenote.py:1684-1692; Notion notion_md.Unkept at docs/decisions.md:687-694). A timeline representation must round-trip on every backend that declares the type.
- Bumping apiVersion would reject every existing external package (manifest.py:136-137), so the change must be additive under apiVersion 1.
- The contract text has already drifted between docs/providers.md and the skill mirror (row count; load fields; retry and the save merged/version fields undocumented). A partial update would violate docs/plugins.md:50-53.
- Search results use section.notes when present (sidebar.js:62-70), so a type on rows only would be missing in search hits and folded-tree inventories.
- isStored compares snapshot title and body strings (NoteSession.qml:364-367). A timeline editor's snapshot must be a deterministic serialization, or no-op saves will be sent and real changes may be skipped.
- Timeline bodies are backend content, which the threat model treats as hostile (docs/security.md:327-333). Event counts and field lengths need bounds, and rendering should be plain text.

## editor

### Summary
ui/NoteEditor.qml (2409 lines) is the whole note pane. Top to bottom it holds the formatting ToolBar, a sheet Column (modified-date line, then the notice title or the editable title TextField, a provider-view Loader, a conflict-review Loader, a notice column), a Flickable with one rich-text TextEdit 'area' plus overlays (quote bars, code slabs, drawn checkbox faces, audio players, image handles), and a NoteSkeleton for loading. It is instantiated once, in Workspace.qml:2824-2886 (id editor, objectName noteEditor). Two clients drive it. Workspace binds provider capabilities, theme, fonts and keybindings and reads or calls about 30 members. NoteSession uses only a document protocol: setNote, restoreDocument, snapshotDocument, requestMarkdown, viewState, restoreViewState, title, documentBase, readOnly, showConflict, clearConflict, clearNotice. A 12-function stand-in in tests/transitions.qml:375-400 proves the session needs nothing more. Today the content type is a per-provider boolean: Workspace binds plain: !provider.markdown, which is the only reader of the provider's markdown flag anywhere in QML/JS. 'plain' is threaded through about 20 branches of NoteEditor and through EditorApi.writable, switching the same TextEdit between PlainText and RichText. A body enters through setNote(title, body, shown): it bumps noteToken to win async races and sets the title under settingText. For Markdown it converts through Markdown.toHtml, which runs Python (services/markdown/qthtml) on stdin with a framed JSON answer. showBody then assigns area.text, refreshes decorations and puts caret and scroll at the top, and shown(ok) tells the session the document really holds the note; only then does the load end. restoreDocument puts back the editor's own form (HTML or plain text) without converting; it is used for drafts. For saving, NoteSession.flushSave takes snapshotDocument() ({title, body in editor form, base}). If it equals stored[path], what the provider is known to hold (commit 5887a8f), no save is sent. Otherwise requestMarkdown converts documentHtml() through Markdown.toMarkdown and passes map.note (trailing blank lines trimmed) and ok to provider.save. Every edit ends in the edited() signal: typing (gated by the native content revision, settingText and readOnly), the title, tools, pastes and undo. Workspace forwards edited() to NoteSession.onEdited, which marks the note dirty and calls provider.noteEdited or starts a 1500 ms timer. The session pushes readOnly, and applyReadOnly preserves caret and scroll. Notices, provider views and the conflict review replace the title and body, and a skeleton shows while loading. Task items round-trip as - [ ] / - [x] to and from <li class=unchecked|checked>. Qt paints a glyph that the editor covers with a drawn rounded box (decoration only). A click on the glyph is Qt's own toggle of one item. Ctrl+1 (tool todo) toggles the checkbox list style, not the checked state, and nothing checks items in order. On the keyboard, the body and the title call shortcut(event) before their own handling, which runs Workspace.handleShortcut first. That function checks modal gates, editor.tools.panelOpen and page keys, then matches in context page/search/editor/workspace, where 'editor' means editor.bodyFocused. Tool bindings run editor.tools.execute, paste bindings run editor.paste/pastePlain, and anything left falls to NoteEditor's rich key logic. Some host-level facts hang off the rich editor: canColorText (native inspector built, feeds theming), tools.actions (feeds the KeybindingRegistry), toolbarHeight (aligns the sidebar header), and hoveredLink and wordCount (view bar). A per-note type would only be known inside provider.load's callback, but setNote('', '') and restoreDocument(draft) run earlier, and drafts are stored in one editor's form, so the type must travel with the document.

The pane owns the title, notices, provider view, conflict review, skeleton, modified date, read-only state, focus routing, the toolbar row height and the edited/statusRequested signals. Each editor implements one small interface: setNote, restoreDocument, snapshotDocument, a body request, viewState/restoreViewState, focusBody, bodyFocused, wordCount and edited. tests/transitions.qml:375-400 already shows the session needs only that.
- Replace the 'plain' boolean with a per-note content-type value (for example text, markdown, timeline). Keep the provider's markdown: bool as the default type so the contract change stays additive.
- Make the type part of the document: include it in snapshotDocument, drafts and 'stored', and pick the editor before setNote or restoreDocument runs.
- Move host-level capabilities off the rich editor: canColorText, the tool registry and its actions, and the toolbar row height. Put them in the always-present pane or in Platform.

- Extract the drawn checkbox face into a shared component. Put the 'check everything above' rule in a pure .pragma library JS module so it can be unit-tested.
- Add a timeline real-key suite and register it in both tests/transition_selftest.py:18 and CMakeLists.txt:99.

## session

### Summary
services/notes/NoteSession.qml is the note-session controller. It owns the open note's identity (currentPath), load generations (noteLoadSeq plus the cancellable loadHandle), the dirty flag, retained save drafts, per-note save epochs, in-flight save counts, pending deletions, path aliases for provisional notes, the merge-conflict review, and `stored` (the "what the provider holds" snapshots). Its editor, provider lookup, version lookup and status reporting are injected (NoteSession.qml:3-11; wired at Workspace.qml:2614-2620). The session is duck-typed against `editor`: a 16-member QtObject fake drives it in tests (tests/transitions.qml:375-400). In the app the editor is always the single static `NoteEditor { id: editor }` at Workspace.qml:2824-2886. That NoteEditor is the whole note pane: tool strip, title field, notices, provider views, conflict review and the rich/plain TextEdit body, all in one `sheet` column (ui/NoteEditor.qml:1843-2399). selectPath flushes the current note and then loads the new one. A load either restores a retained draft synchronously or asks the provider. A provider answer must pass `ownsLoad(path, generation)` twice: when it arrives, and again when editor.setNote reports the document is on screen. Only noteReady and noteUnavailable end a load. An edit flows edited() → session.onEdited() → dirty, then either the provider's noteEdited/saveRequested schedule or the host's 1500 ms timer, then flushSave(). flushSave() snapshots the editor (snapshotDocument, which holds HTML or plain text). If the snapshot equals stored[path] it sends nothing. Otherwise it registers a draft, bumps the epoch, converts with editor.requestMarkdown, and calls provider.save(path, title, body, cb, {view, resolution}). finishSave settles the draft, stored, dirty, the version and any conflict. A save conflict opens the session-owned review (MergeConflict) through editor.showConflict; its retry/continue/resolve callbacks re-enter flushSave. Delete runs through a confirm dialog and session.remove, which locks the note, keeps a recovery snapshot until the provider settles, and restores a draft on failure. The list shows a typed title at once through session.unsavedTitles: a binding over the wholesale-replaced drafts map plus editor.title while dirty. Workspace.displayTitle(row) reads it, and NoteList/SearchResults call it through titleFor(row) (commit 7162589). Content type is per provider today. provider.markdown is read in exactly one place, the editor's `plain:` binding (Workspace.qml:2837-2840). NoteEditor branches on `plain` for conversion, snapshot, text format and tools. Commands and shortcuts converge on one executor. defaults.js entries with workspace:true and manifest commands naming a workspaceAction both call WorkspaceActions.invoke(action), whose handlers take no arguments and share one availability function. handleShortcut resolves modal states first, then does a registry lookup by context (page / search / editor-if-body-focused / workspace). The host state file (version 4) stores no per-note document data, and drafts and `stored` live only in memory. Neither host references the editor or the session.

## local

### Summary
A local note is one UTF-8 file ending in `.md` under the notes root (~/Notes, NOTE_NOTE_DIR or providers.local.notesDir), and its absolute path is its identity (`local:<abs path>`). Folders are notebooks and their sections, with order kept in `.order` and `.notebooks` files and pasted pictures in `.assets/`. The on-disk format has a single owner, plugins/org.note-note.local/notefile.py. It handles a `---` fenced front-matter block that is parsed line by line (it is not YAML, and no YAML parser may be added). The app owns only the first column-0, case-sensitive `title:` line; every other front-matter line is returned verbatim as `extra` and written back after the title line on save. A BOM and CRLF or lone-CR endings are read transparently, and a save always writes LF with no BOM. Content type is per provider today (`markdown: true`, Provider.qml:20). No note carries a type and nothing reads or writes a type key. A hand-written `type: timeline` line already survives every save as an unowned extra line (verified), but the listing, the load answer and search never see it. The listing (list.py) reads only the first 4096 bytes of each note. It emits `N key path title preview size mtime_ns`, which Provider.qml parses into the entry `{key, file, path, title, preview, size, version}`; rows add `version` (mtime ns) and `modified` (ms). The preview is the first non-empty body line with leading `#>*-` markers stripped, so a task item previews as `[ ] Event`. Search (search.py) reads each whole note, capped at 2 MiB, and matches the body only, so front-matter text is never found. The provider caches no bodies: every load runs `operations.py read`, which returns `{title, body, editable, reason, version, bytes}`, and `editable` comes from `qthtml.unkept` (raw HTML, including an HTML comment, makes a note read-only). Create writes `---\ntitle: \n---\n` to a new `note-<uuid hex>.md` through an exclusive atomic link. Save re-reads the current file's extra lines, refuses anything over 2 MiB and commits through `fileio.write_atomic`; there is no version check, so the last writer wins for the body. Delete unlinks the file, there is no per-note rename, and folder delete refuses folders holding anything but `.md`, `.order` and `.assets`. All mutations go through one ordered local queue, and the model changes only after the commit. The listing reruns on open, on inotify events (400 ms debounce) and on the 20 s poll. An external edit reloads the open note only when it has no unsaved edits and no save in flight; otherwise the next autosave overwrites the external body, though external front-matter lines survive. A timeline stored as a GitHub-style task list (`- [ ]` / `- [x]`) in the Markdown body would stay readable and editable in other tools and searchable, and the current Markdown editor opens it editable (`unkept` is empty). A tight item, though, joins title and description into one paragraph. Two traps for any new per-note field: Provider.qml rebuilds the note entry with explicit fields on save (548-549) and rebuilds the load answer the same way (509-511), so both would silently drop it. A readable rendering of this map is at /tmp/claude-1000/-home-andrei-Projects-note-note/b40cb580-758c-4153-b2d0-b8e9d5523701/scratchpad/maps/local.md.

### Recommendations
- Put the marker in the front matter. It is read in the 4 KiB listing head with no load, preserved by today's save path, ignored by search, and shown as a property by outside tools. Do not use a body marker, a file extension or a sidecar.
- Read and write the type only through notefile.py, with one helper used by list.py, operations.py read and save, and create. Never parse it in QML.
- Treat an absent key as Markdown and write the key only for non-default types. Map unknown values to Markdown and keep the line verbatim.
- Consider a namespaced key to avoid colliding with user metadata, and decide before release because the key is permanent on disk.
- Store events in the Markdown body as a GitHub-style task list (`- [x] Title` with an indented description paragraph). Read them with services/markdown/parse.py (task_list_item, attrs.checked) and write them with mdtext escaping. This keeps the note readable, editable and searchable outside the app, and keeps the existing editor able to open it.
- Append the type as a trailing 8th N field, and update selftest FIELDS and the transitions record() fixtures.
- Carry the type through Provider.qml's save commit (548-549) and load mapping (509-511), using Object.assign or explicit propagation, so later fields are not dropped.
- Return the type and a type-aware preview from the save answer, so the row stays consistent without waiting for a relist.
- Tests: notefile property cases with a type line (tests/test_regressions.py:97-110); a selftest round trip over list, read, save, exact bytes and re-read, including CRLF/BOM and a front matter over 4096 bytes; create with a type; unknown type falls back; search finds event text; QML loadList with an 8-field N record.

### Open questions
- Key name and vocabulary: a bare `type:` (collision risk) or a namespaced key? Which values: timeline, markdown, text?
- Does the app own the type key like title (parsed into a field, written by serialize), or keep it as an unowned extra line read through a notefile helper? Can a save or a later action change it?
- Is an absent key the Markdown default? Should the app avoid ever writing `type: markdown`, so existing notes are never rewritten?
- What is the exact timeline body format? Tight or loose task list? How are the event title and description told apart (first paragraph, bold, softbreak)? What about multi-paragraph descriptions, escaping of [ * # in titles, and empty titles?
- What happens with a non-monotonic check state, or non-task-list content, in a timeline note: show as is, normalize on the next check, or open read-only with a reason?
- Must event text be found by body search? Body storage gives that for free; front-matter storage loses it.
- What should a timeline row's preview be (first event, next unchecked event, "k of n")? Must it fit within the 4 KiB head?
- Can an existing note be converted to or from a timeline? If so, a set-type operation is needed in operations.py and the provider.
- Should the local provider offer a plain-text type at all? Today every local note is .md Markdown, and Sticky Notes is the plain-text provider.
- Should local adopt lib/notemerge or a version check so an outside check-off is not overwritten? This is a non-goal for local today.
- How should an older app version, or an unknown future type, open a typed note: as editable Markdown (risking lossy writes for non-Markdown types) or read-only?

### Risks
- The save commit (Provider.qml:548-549) rebuilds the note entry with explicit fields. A `type` field would vanish after the first autosave until the next relist, and the row could flip to the default type or editor.
- The load answer is rebuilt with explicit fields (Provider.qml:509-511), so a type returned by operations.py read would never reach the host unless this mapping changes.
- The listing parses only the first 4096 bytes (list.py:64, 147-153). A front matter longer than that, or a type line beyond it, lists with no title, the preview `title: ...` and no type, while load reads the whole file and sees the type. List and load would disagree (verified).
- A bare `type:` key can collide with metadata from other tools. This is general knowledge, not a code fact: Hugo uses front-matter `type` to pick layouts and many Obsidian vaults use a `type:` property. Such notes open as editable Markdown today; misreading or refusing them would regress.
- There is no YAML parser (pyproject.toml:13-17). Events stored as YAML in front matter would be kept verbatim but need a hand-written YAML subset, and would be excluded from search (search.py:50-52) and from the preview.
- There is no version check on save (operations.py:126-141; Provider.qml:543). A timeline checked in another editor or synced from a phone while the note has unsaved edits is silently overwritten by the next autosave.
- Outside edits can produce a non-monotonic state (`[ ]` above `[x]`) that the check-everything-above rule does not allow, and its handling is undefined.
- Tight task items join title and description with a softbreak, which is ambiguous to read back. Opening such a note in the generic Markdown editor and saving rewrites it as one line (verified: "Kickoff Agree scope").
- Any raw-HTML body marker (for example an HTML comment) makes unkept answer HTML, so the note opens read-only in the Markdown editor, in older app versions and in any Markdown fallback (verified).
- The generic preview keeps the brackets (`[ ] First event`). A progress preview computed from the 4 KiB head would be wrong for long timelines.
- A file-extension marker changes note identity (the path), invalidates .order names, needs five .md filter changes, and breaks readable-by-any-tool if the extension is not .md.
- A sidecar file would block folder delete (operations.py:60-68) and trigger relists.
- Titles are written raw with no YAML quoting (notefile.py:75), so strict-YAML tools may misread titles containing `: `, `#` or leading quotes. This gap already exists and adding keys does not change it.
- Docs and behavior differ: the docs say a note over 2 MiB opens read-only, but it loads as an error and the host shows it unavailable with no content (operations.py:114-116; NoteSession.qml:257-259; technical-requirements.md:174).
- Context only, not at HEAD: the untracked CODE-REVIEW-2026-10-11.md in the working tree reports that row actions (folder rename and delete) do not wait for the open note's save (its F2). Typed notes would share that race.

## onenote

### Summary
The OneNote provider (plugins/org.note-note.onenote) is a LaneProvider. It declares its content type once for the whole provider: markdown: true, hasTitle: true, canImages: true, plus a tools list that leaves out quote, code, codeblock and rule (Provider.qml:16-37). The host reads that flag in exactly one place, editor.plain = !p.markdown (Workspace.qml:2837-2840). onenote.py also puts a per-page 'markdown: True' field on every load answer (onenote.py:1380-1381, 1387), but nothing in the host reads it; NoteSession consumes only error, version, base, title, body, view, editable, reason, recovered, conflict and retry. Loading a page means GET contentUrl?includeIDs=true, then onenote_md.html_to_markdown, then the shared merge journal, which normalises every snapshot by running Markdown to OneNote HTML and back (onenote.py:1286-1306, 1344-1387). To-do note tags map both ways. On read, data-tag 'to-do' / 'to-do:completed' on a <p> becomes '- [ ] ' / '- [x] ', and on a <span> inside a list item becomes '[ ] ' / '[x] '. On write, a top-level list made only of task items becomes <p data-tag> paragraphs; any other task list becomes <li><span data-tag>. A checkbox-only change keeps the original HTML carrier and flips just its ':completed' suffix (onenote_patch.py:143-165). Creating a page is a single XHTML POST whose head holds only <title>; it is never retried, and the provider always creates with an empty title and body. Neither create() nor the create payload carries any content type. A save takes several steps. First it refuses unkept constructs, then stages the draft, re-reads the page and three-way merges it (lib/notemerge snapshots hold only title and body). Then onenote_patch.plan turns the merged result into element-level PATCH commands addressed by generated IDs. The plan is simulated and must reproduce the merged body exactly, keeping every unchanged ID and attribute. Unsupported edits raise UnsupportedEdit and keep the draft; there is no whole-page fallback. Blank lines are removed first, through the undocumented web revision service, and the title goes in its own PATCH. I ran the pure functions to test timeline shapes. A to-do paragraph with a bold title, followed by a paragraph indented 36px holding a one-line description, round-trips losslessly. On that shape the planner turns check-k-and-above, append, insert, edit and delete into minimal commands. It refuses to insert a repeated title mid-list, and a reorder re-creates the moved event. Several existing to-do and indent paths lose data or misread it: multi-line indented descriptions, <br> inside a to-do, task items with continuation lines, a leading tag emoji, priority to-dos, multi-tag values and tags on headings. Microsoft Learn documents no durable custom page-level marker. Custom <meta> is undocumented and meta/head support no PATCH actions; custom note tags are unsupported; a note tag on the title is not returned; the page resource has no custom properties; and no hiding CSS exists. data-id is a documented input/output attribute, and this repo measured that it survives Graph updates. Microsoft does not document whether it survives edits in the OneNote apps, and a 2021 Microsoft Q&A thread reports data-ids vanishing. OneNote apps toggle each to-do independently, and the merge combines checkbox changes per entry, so the 'checking k checks everything above' rule cannot hold for OneNote content. My recommendation is to defer OneNote timelines in the first release. OneNote should declare only its current Markdown type, and the event body shape should stay OneNote-compatible so a later release can opt in after live verification of a marker.

### Recommendations
- First release: defer OneNote timelines. OneNote declares only its existing Markdown type in the new contract, and the host offers no 'New timeline' in OneNote notebooks. Reasons: no documented durable marker; meta cannot be added after creation; custom tags are unsupported; data-id survival in the OneNote apps is unverified, with a negative report; the 'check everything above' rule cannot be enforced in OneNote; and several existing to-do and indent paths lose data.
- Keep the cross-provider timeline body representable in OneNote's verified-stable shape: per event, one to-do paragraph with a bold single-line title, plus at most one indented single-line description paragraph. Then a later release can opt OneNote in without migrating content.
- Before enabling OneNote timelines, verify a data-id wrapper-div marker live (create via Graph, edit, add and check events in desktop, web and mobile, re-read via Graph). Record the results in a dated docs/onenote-*.md section, as done for blank lines and page order.
- Treat a lost marker as graceful degradation to a Markdown checklist note, and never write anything to 'restore' it without the user's action.
- Fix the to-do converter edge cases independently of the timeline feature: multi-tag values, priority tags, tags on headings, task continuation lines, leading emoji, and NBSP indentation after hard breaks. Each currently loses data silently in ordinary OneNote notes.
- Make the timeline view tolerate check states that break the ordering rule, and define unchecking semantics explicitly. OneNote apps and the per-entry merge will produce non-monotone states.
- Prefer 'Add new event' appending at the end. It uses the planner's unchanged-prefix path, which tolerates repeated titles; mid-list inserts of repeated titles are refused.
- Do not use the undocumented web revision service, a custom note tag, a hidden element or a <meta> for the marker.

### Open questions
- Does a data-id written via Graph (on a wrapper div or on paragraphs) survive edits in OneNote for Windows, Mac, the web, iOS and Android? Does copy-paste inside OneNote duplicate it?
- Does Graph keep and return a custom <meta name='...'> in the page head at all? The docs say unlisted tags are 'probably ignored'; this is unverified.
- How does Graph return an indented paragraph made in a OneNote app (margin-left px/pt, or something else)? Does the document order of several outlines match the visual order a user sees?
- How should a timeline page that breaks the 'everything above is checked' rule (after OneNote or merge edits) be shown: as is, repaired on display, repaired on save, or refused?
- What does unchecking an event mean: only itself, or every event below it? The request does not say.
- May an existing OneNote page be converted into a timeline, or back? If so, by inserting a marker element, or by a title change?
- Should an empty timeline (no events yet) exist as a OneNote page, and where would its marker live if the body is empty? Graph may drop an empty div.
- When a marker is lost in OneNote, should the app fall back to Markdown, or remember the type locally per page?
- Is a user-visible title convention acceptable under the project's 'no hacks' rule, given it is the only marker documented to survive every OneNote app?
- Should the timeline body shape be shared across providers, with OneNote rendering it as to-do paragraphs plus indented descriptions, or should each provider own its own serialisation?

### Risks
- No documented, durable, machine-readable page marker exists. A data-id marker's survival in OneNote for Windows, Mac, web and mobile is undocumented, and a Microsoft Q&A thread reports data-ids vanishing. A lost marker silently turns a timeline into a checklist note (graceful: no content lost, but the type is lost).
- A custom <meta> marker is undocumented and could be written only at creation (meta and head support no update actions). It would make existing pages unconvertible, and it may be dropped by Graph itself.
- OneNote apps toggle each to-do independently, and the merge combines checkbox changes per entry (merge_selftest.py:1117-1123). Timeline pages will therefore arrive with states that break 'everything above is checked'.
- Multi-line event descriptions (consecutive indented paragraphs) lose their indentation on lines after the first. Load normalisation shows them unindented, and an unrelated save rewrites them in OneNote (onenote_md.py:280-281 plus the shared parser's NBSP stripping after hard breaks).
- Task items with continuation lines or paragraphs, and task titles starting with a tag emoji, are flattened silently at staging; unkept_formatting does not refuse them.
- A <br/> inside a to-do paragraph is flattened when its checkbox is toggled.
- Priority to-dos lose their priority on a text edit. A multi-tag 'to-do:completed, …' reads as unchecked, and checking it writes a malformed data-tag. Tags on headings are invisible and dropped on edit.
- Inserting an event whose title repeats an existing one anywhere but the end refuses the save (AmbiguousAlignment -> UnsupportedEdit). Reordering re-creates the moved event: its identity is lost and phone sync may duplicate it (engine-notes.md:606-618).
- The listing has no page content, so a type cannot be shown in the sidebar for unopened pages without an extra GET per page (400/hr budget), unless it comes from the search cache or a title convention.
- A title-based convention is visible and user-editable, and title PATCHes fail on some older pages (engine-notes.md:532-536).
- Merge snapshots hold only title and body, so a type kept outside the body is not recovered with drafts or merged.
- Graph reads are eventually consistent (engine-notes.md:645-647), so a marker written at creation may not appear on an immediate re-read.

## notion-sticky

### Summary
Both providers extend services/providers/LaneProvider.qml. It supplies a 1500 ms save debounce, one request lane per rate key ('notion' at 3 requests/s, 'graph-mail' at 240/min), one python3 process per job, and a session guard that refuses answers arriving after a sign-in change. Today the content type is per provider: Notion declares markdown: true and Sticky declares markdown: false. Workspace.qml turns that into the editor's plain flag (plain = !provider.markdown), which switches the TextEdit to PlainText, bypasses the Markdown converter and makes EditorApi unwritable for every tool. Notion also declares hasTitle: true, canCreate/canDelete true, and no canImages (so false). It has no search(), because the API searches titles only. Its tools whitelist has 19 ids, including todo but not table or textColor. notion.py is pinned to Notion-Version 2022-06-28. It lists pages with POST /search, keeping only id, title, parent and edited. It loads a page with GET /pages plus a recursive block fetch on a 300-block budget, and converts the blocks to the editor's Markdown dialect in notion_md.py. notion_md maps to_do blocks to '- [ ]'/'- [x]' task items and writes checked back. Headings 1-3 become '#' lines, consecutive paragraphs become lines joined by hard breaks, and a newline inside an item becomes a Markdown hard break. Children nest only under bulleted, numbered and to_do items, two spaces per level. A page opens editable only if its blocks survive blocks -> Markdown -> blocks with every property equal (notion_md.unwritable/essence); otherwise it opens read-only with a reason naming what Note Note cannot write back. A save works in this order: it converts the Markdown to blocks (refusing anything Notion has no block for via Unkept), re-runs unwritable on the live page, PATCHes the title only if it changed, appends every new top-level block, and only then DELETEs every old top-level block. So every save replaces the whole page, block ids included. Create POSTs /pages under the open page, because the API cannot create top-level pages, and is never re-run after an uncertain 5xx; the QML always sends an empty title and body. Probes against HEAD show what round-trips unchanged: one to_do per event holding 'title\ndescription' in its rich text (plain or bold title), and to_dos with to_do or bulleted children. They also show what breaks: a to_do with a paragraph child (a common Notion edit) opens read-only, a callout marker opens read-only, and a multi-paragraph description is refused by the writer. A parent page holding a child_page also opens read-only, and every new note created under the open page puts one there. The Notion API has no invisible per-page metadata: a page whose parent is a page may hold only the title property, and pages and blocks have no custom or app fields. So every durable timeline marker is either visible or not durable: the page icon, a marker block, a database property (database pages only, and against the no-databases non-goal), or a local map kept by Note Note. Notion's UI shows to_do blocks as a checklist, which reads sensibly as a timeline, but lets the user check any item on its own, so the 'check all above' rule can be broken from Notion. Notion's Update-a-block endpoint can flip a to_do's checked state alone, but the provider keeps no block ids after load, so today every check is a whole-page rewrite costing about N DELETEs at 3 requests/s. Sticky Notes declares markdown: false, hasTitle: false (the subject mirrors the first line), no tools and no images, and answers search() from memory because the listing carries every body. sticky.py reads bodies as plain text (Prefer: outlook.body-content-type="text"). A save PATCHes a text body plus a subject equal to the first non-empty line cut to 255 characters; the title argument is ignored. A create makes an empty message stamped with the extended property String 0x001A = IPM.StickyNote. A Sticky timeline could only be an invented plain-text syntax, shown raw by Microsoft's apps, or a custom named extended property whose survival through Microsoft's clients is unverified; the documented decision forbids inventing behaviour the backend cannot keep. Recommendation: defer the timeline type for Notion (Markdown only in the first release), and treat Sticky Notes as unsupported (plain text only).

### Recommendations
- Notion: DEFER the timeline type in the first release, and declare Markdown only (today's behaviour). Reasons: no invisible durable marker exists (title-only properties, no app metadata), so any marker is a visible product decision the user has not made. Notion's UI does not keep the 'all above checked' rule. Common Notion edits (a nested paragraph) turn the page read-only. Every check costs a whole-page rewrite at 3 requests/s.
- Notion, when support comes later: store one to_do per event with 'title\ndescription' in its rich text (bold title allowed); probes A/B round-trip through the unchanged notion_md. Limit descriptions to one paragraph. Choose the marker explicitly (the page icon over a marker block, since a callout is unwritable today) and re-check it in cmd_update the way unwritable is re-checked. Optionally add targeted 'checked' updates via Update a block.
- Sticky Notes: UNSUPPORTED; declare plain text only. Reasons: the backend is plain text with no title, the editor runs in plain mode with no tools, a timeline would be an invented syntax shown raw in Microsoft's apps (which decisions.md:557-561 rules out), and marker persistence through Microsoft's clients is unverified.

- Map today's booleans onto the new declaration without breaking external providers: Notion markdown: true becomes Markdown, Sticky markdown: false becomes plain text, and examples/hello and external providers keep working.

- Where should a Notion page's content type live: the page icon, a marker block, a local map kept by Note Note, or a property (database pages only)? This is a product choice for the user.
- On load, should a Notion timeline whose checks are non-monotonic (edited in Notion) be normalised, which costs a write, or shown as it is?

### Risks
- Notion has no invisible per-page metadata. A durable type marker is either user-visible and user-editable (icon, marker block) or not durable (a local map in Note Note). A user who changes or removes the icon in Notion silently turns the type back into Markdown.

- Sticky: whether a custom named extended property or open extension survives edits in Microsoft's Sticky Notes clients is unverified.

## ui-design

### Summary
The sidebar (ui/NoteList.qml) renders a plain JS array of rows that services/notes/sidebar.js builds. Its row() copies only a whitelist of provider fields: kind, path, title, hasTitle, preview, icon, reorder, level, expanded, count, menu and modified. No per-note content-type field exists anywhere on this path. Note rows are drawn by the shared ui/NoteSummary.qml, which ui/SearchResults.qml also uses: a bold elided title, then a second line of date (HH:mm today, otherwise 'd MMM') and a whitespace-collapsed, elided preview. Note rows draw no icon, even though row() carries `icon`; only action, new and tree rows draw glyphs. Rows have no unsaved marker. Unsaved state shows only in the view bar for the open note, plus a typed title projected through session.unsavedTitles into Workspace.displayTitle. The workspace compares rows with JSON.stringify before assigning them, and a recorded decision says a row carries only what the list shows. A type field therefore has to be something the list draws, and a timeline progress summary placed in `preview` would be searchable, would become the untitled-title fallback, and would lag until the provider re-lists. Form building blocks are: PromptDialog (a modal with one TextField; Enter submits a non-empty value, Escape or the scrim cancels; sized in raw pixels); ConfirmDialog (keys driven by the workspace); ToolForm (a popover card with header, fields, a hint and an 'Insert' button, hard-bound to an editing Tool and its editor); TextField and ChromeTextField (single-line, optional leading glyph); Button and ChromeButton (keyboard focus is opt-in); and SidebarAction (a footer row that becomes a single-line field in place). There is no multi-line input control in the design system; only a read-only QQC.TextArea in MergeConflict and plain TextEdit pages exist. Creation is provider-driven through footer actions, row menus and '+ New note…' tree rows. The host adds no creation buttons, the footer `shortcut` vocabulary is only newNote and newNotebook, and both workspace actions and host.newNote(providerId, target) take no type. Row menus open only on right-click, so they have no keyboard path. The command palette exposes parameterless `workspaceAction` commands and a generic ui.pick picker. Colours come only from design/tokens.js (63 tokens) through the Color singleton. Hover, pressed and selected fills come from Style.*FillFor. 'Accent as ink' is Qt.tint(foreground, alpha(accent, 0.6)), and Qt.lighter/Qt.darker are explicitly forbidden. The editor already draws a themed checkbox: accent fill with the tick cut out in the background colour, and a 0.4-alpha border when unchecked (0.75 on hover). Circle precedents are the text-colour swatches (2 px accent focus ring) and the audio player. The Omarchy shell's Style exposes more spacing and font keys than the standalone fallback objects, so shared code may only use the intersection. Glyphs are Nerd Font Material Design literals drawn with Style.fontFamily; the bundled Nimbus Sans interface font has none, and standalone registers a Symbols Nerd Font fallback. Accessibility is thin: only Accessible.name is used, and there is no Accessible.role, activeFocusOnTab or KeyNavigation anywhere. Keyboard work is explicit Keys handlers plus forceActiveFocus. Workspace.handleShortcut routes keys, giving modal states the first claim, and Escape means 'back' (clear the search or hide the window) in the notes context. The business requirements demand that note work never needs the mouse and that no modal dialog stands between the user and their text.

### Recommendations
- Extend NoteSummary once with a type-glyph slot and an optional progress text, so the list and search stay identical. Keep the type-to-glyph/label mapping in one host-owned module, like services/notes/sidebar.js, so rows, footer, menus and palette agree without provider-id branches.
- Draw the timeline check circle with the editor's checkbox recipe made round (radius side/2). Unchecked: border alpha(fg, 0.4), 0.75 on hover. Checked: accent fill with the tick in the background colour. Focus: a 2 px accent ring as on the TextColor swatches. ## extensibility

### Summary
Every package is one folder with a plugin.json. Built-in packages live in plugins/ and user packages in $XDG_CONFIG_HOME/notenote/plugins/; one Python helper (services/extensions/manifest.py) discovers both. PluginCatalog.qml runs that helper once per process, after settings load, without executing any QML, and publishes one descriptor array per kind: commands, keybindings, themes, providers, tools. Validation is strict. schemaVersion and apiVersion must be exactly 1, any key under contributes outside KINDS rejects the whole package, package IDs are reverse-DNS, and org.note-note.* is reserved for built-ins. Resources must be relative regular files, read through no-follow directory descriptors with byte, count and deadline caps. Trust is a settings switch: data-only packages (themes) load by default, while any package holding commands, tools or providers is 'executable' and, if it comes from the user, starts disabled until plugins.<id>.enabled is true. Built-ins are enabled by default and can be disabled, except the protected org.note-note.appearance; every package change needs a restart, and nothing is hot-unloaded. QML is trusted code with no sandbox, loaded three ways. Providers are created with Qt.createComponent in Workspace.addProvider and given host and services. Tools are created eagerly, once per editor, by ToolRegistry (PreferSynchronous) and given an EditorApi. Command handlers are created lazily, once per invocation, by CommandRegistry (Asynchronous) and given a context API object. The public NoteNote.Extensions 1.0 module (Command, Tool) is an import root each host registers. The standalone host always registers it, but Omarchy only does when the optional native module is built, which is why always-on built-ins (the calendar tools, the providers) use repository-relative imports instead. The only extension-API versioning is an exact-match integer: apiVersion 1 in the manifest and apiVersion: 1 on each QML object. Tools were added as the fifth kind (commit 2c5920f) without bumping it, and that commit is the template for a sixth kind. It touched manifest.py and its selftest, PluginCatalog.qml, a contract QML plus a public wrapper and a qmldir line, a registry, one wiring line each in Workspace.qml and NoteEditor.qml, the docs, the plugin-author skill and its check.py, an example package and tests. Built-in contributions are mostly packages: calendar (tools), appearance (themes plus a command), workspace (data-only commands) and the four providers. The exception is the core formatting tools, which live in ui/tools/ outside any package and cannot be disabled. So a built-in timeline type could ship as plugins/org.note-note.timeline/, dogfooding the contribution point the way calendar does for tools, but the user could then disable it. Existing precedents leave absent contributions dormant rather than rewritten: layouts keep naming missing tools, bindings stay dormant, and a missing theme falls back to System without changing saved settings. Together with the rule 'open read-only rather than risk a bad write', they define what should happen to notes whose type package is disabled or removed. Note content is assumed hostile, so a type codec must bound what it parses and fail closed. No per-note content type exists anywhere today. The editor's only format switch is plain = !provider.markdown (Workspace.qml:2837-2840), and the toolbar, keyboard context and word count all assume the single TextEdit document.

### Recommendations
- Add note types as the catalog's sixth kind, following the tools precedent (commit 2c5920f). Extend KINDS, BUILDERS and `executable`, add a PluginCatalog property, add an app-owned contract QML with apiVersion 1 re-exported through a NoteNote.Extensions qmldir line, and add a registry modelled on ToolRegistry: null until the catalog is ready, PreferSynchronous creation, ID matching the manifest, built-ins win, diagnostics, load once. Keep apiVersion 1, as the tools kind did.
- Put display metadata (title and an icon glyph) in the manifest so pickers and the list can name types without instantiating code, as commands do. Keep the editor Component and the codec in the type's QML.
- Ship the timeline as plugins/org.note-note.timeline/ with relative imports, as the calendar package does, so it works in Omarchy without the native helper. Keep plain text and Markdown always available, either as app-core types or a protected package, to act as the fallback, the way System does for themes.
- Open a note whose type is not loaded read-only, with a visible reason and its raw body. Never re-serialize it through another type, and preserve its type marker. This follows the theme, toolbar and binding precedents and the rule 'read-only rather than lossy'.
- Prefer qualified type IDs for package-contributed types, so a later built-in cannot take over a user type's notes. Decide separately whether the core types get short reserved names.
- Make the codec bounded and fail-closed: cap the number of events and the size of each title and description, and open an unparseable body read-only with a reason.
- Update everything in the same commit: docs/plugins.md, the plugin-author skill (SKILL.md, a new reference, check.py), the README 'Writing plugins' section, a decision record, an example package, and the tests (manifest selftest, extensions harness, a registry validation test).

### Open questions
- What is the manifest key and descriptor shape (noteTypes or contentTypes), and which fields live in the manifest (title, icon) versus in QML (editor component, codec)?
- Should type IDs be qualified (<package-id>/<local-id>), like themes and commands, which are persisted in config.json, or unqualified, like providers and tools? And how does each provider persist the type per note?
- Are plain text and Markdown app-core types (a ui/ folder, like ui/tools) or a protected built-in package (which would turn PROTECTED into a set)?
- Is there one type registry per workspace (stateless codecs) or one per editor (like ToolRegistry)? Where is the editor component instantiated, and when is it destroyed relative to pending saves?
- How do sidebar previews and content search work for typed notes when providers compute them in Python?
- Does docs/business-requirements.md:57-58 (no databases, templates or plugins-inside-the-plugin) need amending for note types?
- How should a note whose type is not loaded open: strictly read-only with its raw body, or editable as Markdown or plain text with the type marker preserved (local front matter keeps unknown lines)?
- What API object does a type editor component receive (its model, an edited signal, readOnly, style, colors, fonts, status reporting)? Today providers get services.style and services.colors, and tools get editor.
- May a type package contribute tools or commands scoped to its type, and is the provider `tools` capability list the right gate for that?
- How is 'New note of type X' invoked, given that WorkspaceActions.invoke and the provider's create(target, cb) carry no type?

### Risks
- A broken or hostile type editor runs in-process, in the Omarchy shell's shared QML engine, so an infinite loop or crash takes down the whole shell (cpp/extensionruntime.h:7-8; docs/commands.md:21-25).
- A built-in type package that imports NoteNote.Extensions fails in Omarchy when the native helper is not built, leaving notes of that type unusable (hosts/omarchy/Backend.qml:15-19; ui/editing/ToolRegistry.qml:113-118).
- Built-in packages can be disabled (services/extensions/manifest.py:203-206). Timeline notes would then have an unloaded type, and the structure is lost if a non-type-aware editor saves them.
- An unqualified type ID stored in notes could later be taken over by a built-in of the same ID, since built-ins win (services/extensions/manifest.py:268-283). Existing notes would then be parsed, and possibly rewritten, by a different codec.
- Older app versions reject a whole package that declares an unknown kind, including its other contributions, and there is no minimum-app-version field (services/extensions/manifest.py:142-144).
- Catalog, providers and notes load asynchronously, so a typed note could open before the type registry is ready unless opening is gated (Workspace.qml:839-845, 2474-2483).
- The codec parses hostile input, so unbounded event counts or field sizes would violate the security rules, and truncating would lose data (docs/security.md:16-39, 231-237).
- Provider-side previews and search run in each provider's Python and cannot call a QML or JS extractor from a type package; there is no precedent for cross-package Python imports (plugins/org.note-note.local/notefile.py:79-86; plugins/org.note-note.local/search.py:31-54).
- The toolbar, shortcut context, word count and `plain` gates all assume the TextEdit document, so a type editor beside it needs explicit stand-down logic (ui/editing/EditorApi.qml:13; Workspace.qml:2168-2176, 2920).
- ToolForm is hard-typed to a Tool, so reusing it for the 'Add new event' form needs a generalization (ui/editing/ToolForm.qml:13).
- Exact-count and exact-list test assertions break if the timeline package also contributes tools or commands (tests/extensions.qml:374-375; services/extensions/selftest.py:37-55).
- The docs and the plugin-author skill can drift apart; that has already happened once (an untracked review note at HEAD's working tree lists the provider row shape missing `count`).
